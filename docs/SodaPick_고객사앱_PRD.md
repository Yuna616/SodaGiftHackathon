# PRD: SodaPick 고객사(스폰서) 앱

> 상위 문서: `SodaPick_기획안.md`, `SodaPick_PRD.md` (통합본), `SodaPick_유저앱_PRD.md` (참가자용, 자매 문서)
> 이 문서의 목적: 캠페인을 개설·운영하는 스폰서(엔터사/브랜드) 쪽 화면을 실제 빌드 가능한 수준까지 상세화
> 기준 시나리오: 유저앱 PRD와 동일하게 **"K팝 컴백 위클리 픽"** 기준으로 서술

---

## 1. 목표 & 성공 지표

**제품 목표**: 스폰서가 예측 캠페인을 직접 설계·발행하고, 리워드 예산을 투명하게 통제하며, 판정부터 지급까지 오케스트레이션 전 과정을 신뢰할 수 있게 만든다. 그 신뢰가 다음 컴백에도 다시 SodaPick을 쓰게 만드는 근거가 된다.

**성공 지표 (실 서비스 기준 — 해커톤 데모에서는 정성적 시연이 우선이지만 설계 시 아래를 염두에 둘 것)**

| 지표 | 정의 |
|---|---|
| 캠페인 생성 완료율 | 마법사 진입 대비 발행(활성화) 완료 비율 |
| 온보딩 소요시간 | 첫 로그인부터 첫 캠페인 발행까지 걸린 시간 |
| 예산 집행 정확도 | (실제 지급액 ÷ 사전 추정 소요예산) — 1에 가까울수록 예측 정확도가 신뢰를 뒷받침 |
| 지급 실패율 | `POST /v1/orders` 실패 건 ÷ 전체 클레임 건 — 낮을수록 "약속된 보상을 실제로 이행"이라는 핵심 가치제안이 증명됨 |
| **재캠페인율 (북극성 지표)** | 한 번 캠페인을 발행한 스폰서가 다음 컴백/이벤트에서 다시 캠페인을 만드는 비율 — 이 제품이 실제로 반복 수익을 만드는지 보여주는 핵심 숫자 |

## 2. 스코프 가드레일

| 가져와도 되는 것 | 가져오면 안 되는 것 |
|---|---|
| 캠페인/라운드 생성, 카탈로그 큐레이션, 예산 게이트(경고), 판정 콘솔, 지급 모니터링, 종료 리포트 | 소다기프트 지갑 충전 UI 자체 재구현(충전은 소다기프트 대시보드로 딥링크), 세금계산서·정산서 발행, 환율/통화 변환 로직 직접 계산 (전부 소다기프트 인프라의 책임 영역) |
| "판정 확정 전 미리보기로 영향받는 참가자 수 확인" | 판정 확정 후 정답 되돌리기(대신 별도 "이의제기" 트랙만 허용 — 신뢰 계층 훼손 방지) |

## 3. 타겟 유저 & 대표 시나리오

**페르소나 예시 — "민준", 34세, K팝 엔터사 글로벌마케팅팀 매니저**
해외 팬덤 대상 마케팅 예산을 매 컴백마다 집행하는데, 지금까지는 크로스보더 경품 지급을 위해 배송대행업체를 따로 컨택하거나 국가별로 상품권을 수기로 구매해 이메일로 뿌려왔다. 매번 "몇 명이 당첨될지 모르는데 예산을 어떻게 잡지", "이 나라엔 이 상품권이 있나" 하는 고민을 반복해왔다.

**시나리오**: 민준은 신곡 발매 3일 전 SodaPick에 로그인해 캠페인 마법사를 시작한다. 그룹명·기간·4주치 라운드 질문을 입력하고, 카탈로그에서 자사 굿즈스토어 카드와 해외팬용 범용 상품권을 함께 선택한다. 예산 게이트 화면에서 "예상 당첨자 620명 기준 최소 $4,960 필요"라는 안내를 보고 소다기프트 대시보드로 이동해 지갑을 충전한다. 캠페인을 발행하고, 매주 라운드가 마감될 때마다 판정 콘솔에서 정답을 확정한다. 지급 현황 화면에서 실시간으로 몇 건이 지급 완료됐는지 확인하고, 캠페인 종료 후 리포트를 팀 회의 자료로 그대로 캡처해 쓴다.

이 시나리오 하나가 이 문서에서 정의하는 모든 화면·기능의 존재 이유다.

## 4. 상세 유저 플로우 (엣지케이스 포함)

1. **캠페인 생성 시작** (기본정보: 제목, 아티스트명, 기간, 라운드 수)
   - 엣지케이스: 필수 정보 누락 시 다음 단계로 진행 불가, 임시저장(draft) 상태로 언제든 이어서 작성 가능
2. **라운드별 질문 설계** (질문 텍스트 + 4지선다 옵션 + 판정 기준 서술 + 예상 당첨자 수)
   - 엣지케이스: 판정 기준 서술이 비어 있거나 너무 짧으면("나중에 정할게요" 등) 저장은 허용하되 발행 전 마지막 검토 단계에서 경고 배너 노출 — 모호한 기준은 사후 이의제기 리스크로 직결되기 때문
   - 엣지케이스: 예상 당첨자 수는 스폰서가 직접 입력한다(자동 계산 아님). 0 이하 입력은 저장 불가, 미입력 상태로는 다음 단계(예산 게이트) 진입 불가
3. **리워드 카탈로그 구성** (`GET /v1/products` 목록에서 체크박스 선택)
   - 엣지케이스: 자사 관련 상품이 카탈로그에 없는 경우 → "자유선택 카탈로그만 노출" 상태로 자동 전환, 경고 없이 정상 진행 가능(선택 사항이지 필수 아님)
4. **예산 게이트 확인** (`GET /v1/accounts/balance` vs 스폰서가 입력한 예상 당첨자 수 기준 추정 소요예산 비교)
   - 엣지케이스: 잔액 부족 시 캠페인 **활성화(공개) 자체를 차단**, "소다기프트 지갑 충전하기" 딥링크 제공. 충전 완료 확인은 재조회 버튼으로 수동 트리거(웹훅 없이도 데모 가능)
5. **캠페인 발행 (활성화)**
   - 엣지케이스: **발행 후에는 질문·옵션·정답 판정기준 수정 불가** (참가자 신뢰 보호를 위한 물리적 제약). 수정이 필요하면 캠페인을 내리고 새로 발행해야 함 — 이미 제출된 예측이 있는 경우 재발행 시 경고
6. **라운드 판정 입력**
   - 엣지케이스: 판정 확정 전 "영향받는 참가자 수 / 예상 지급액" 미리보기 필수 노출, 확인 버튼 한 번 더 요구(실수 방지)
   - 엣지케이스: **판정 확정 후에는 되돌릴 수 없음** — 오판정이 의심되면 "이의제기" 별도 트랙(운영팀 검토 필요)으로만 처리, 판정값 직접 수정 기능은 존재하지 않음
7. **지급 모니터링**
   - 엣지케이스: `POST /v1/orders` 실패 건(재고 품절, API 오류 등) 발생 시 대시보드 상단에 뱃지로 표시, 재시도 버튼 제공(`external_reference_id`는 그대로 유지해 중복지급 방지)
8. **캠페인 종료 & 리포트**
   - 엣지케이스: 예산 소진 전 조기 종료 시 잔여 예산은 소다기프트 지갑에 그대로 남아있음을 명확히 안내(SodaPick이 잔여금을 갖지 않는다는 신뢰 메시지)

## 5. 화면별 상세 스펙

### 5.1 대시보드 홈
- 구성: 진행중/예정/종료 캠페인 리스트, 지갑 잔액 요약 카드, 지급 실패 알림 뱃지

### 5.2 캠페인 생성 마법사
- 단계: 기본정보 → 라운드 설계 → 카탈로그 구성 → 예산 확인 → 최종 검토·발행
- 각 단계는 임시저장되며 이전 단계로 돌아가 수정 가능(발행 전까지만)

### 5.3 라운드 질문 설계기
- 구성: 주차별 탭, 질문 텍스트 입력, 4지선다 옵션 입력, 판정 기준 서술란(필수 권장, 미입력 시 경고만), 예상 당첨자 수 입력(스폰서 직접 입력, 필수)

### 5.4 리워드 카탈로그 구성기
- 구성: `GET /v1/products` 결과 그리드(국가 필터 없이 전체 노출), 체크박스 선택, "참가자 자유선택 허용" 토글

### 5.5 예산 게이트 화면
- 구성: 현재 잔액(`GET /v1/accounts/balance`), 라운드 설계 단계에서 스폰서가 입력한 예상 당첨자 수 × 평균 단가 계산식 노출, 부족 시 경고 배너 + 충전 딥링크, 충분 시 안심 배너

### 5.6 캠페인 상세/모니터링
- 구성: 라운드별 참여자 수, 예측 분포 막대그래프, 누적 지급액 vs 잔여 예산 게이지

### 5.7 라운드 판정 콘솔
- 구성: 4지선다 중 정답 선택 라디오, "영향받는 참가자 N명 / 예상 지급 $X" 미리보기, 확정 버튼(더블 컨펌 모달)

### 5.8 지급 현황 & 실패 재시도
- 구성: 클레임 목록 테이블(참가자·상품·상태), 실패 건 필터, 재시도 버튼

### 5.9 캠페인 종료 리포트
- 구성: 총 참여자, 라운드별 정답률, 총 지급액, 참가자 국가 분포(파이차트), 캡처해서 바로 공유 가능한 요약 카드

### 5.10 팀원 권한 관리 *(MVP 스코프 밖, 차기 버전 후보로만 표기)*

## 6. 기능 요구사항 (Acceptance Criteria)

| ID | 요구사항 | 완료 기준 |
|---|---|---|
| FR-1 | 캠페인은 발행 전까지 임시저장 상태를 유지해야 한다 | 마법사 중단 후 재접속 시 마지막 입력 지점부터 이어서 작성 가능 |
| FR-2 | 캠페인 발행은 예산 게이트를 통과해야만 가능하다 | 잔액 < 예상 소요예산인 경우 "발행" 버튼 비활성화, 충전 딥링크 노출 |
| FR-3 | 발행된 캠페인의 질문·옵션·판정기준은 수정 불가능하다 | 발행 후 해당 필드는 읽기 전용으로 전환, 수정 UI 자체가 노출되지 않음 |
| FR-4 | 라운드 판정은 확정 전 영향도 미리보기를 반드시 거쳐야 한다 | 미리보기 화면을 거치지 않고 바로 확정 API가 호출되는 경로가 존재하지 않음 |
| FR-5 | 판정 확정 후에는 정답값을 직접 수정할 수 없다 | 확정된 `Round.correct_option_index`를 변경하는 UI/API 경로가 존재하지 않음 (이의제기 트랙만 별도 존재) |
| FR-6 | 지급 실패 건은 중복지급 없이 재시도 가능해야 한다 | 재시도 시 동일한 `external_reference_id`로 `POST /v1/orders` 재호출 |
| FR-7 | 캠페인 종료 리포트는 별도 데이터 가공 없이 바로 공유 가능한 형태여야 한다 | 리포트 화면 스크린샷만으로 팀 공유 자료로 쓸 수 있는 레이아웃 |

## 7. 데이터 모델 (스폰서 앱 기준)

`Sponsor`, `Campaign`, `Round`는 통합 설계문서(`SodaPick_MVP설계.md`)의 정의를 그대로 따름. 스폰서 앱 전용으로 아래를 추가한다.

- **BudgetEstimate**: id, round_id, expected_winner_count *(라운드 설계 단계에서 스폰서가 직접 입력, `rounds` 테이블에 저장)*, avg_reward_value, estimated_total *(둘 다 예산 게이트 화면 진입 시 실시간 계산, 저장하지 않아도 무방)*
- **ResolutionAuditLog**: id, round_id, resolved_by(sponsor user id), correct_option_index, resolved_at *(판정 불변성 보장을 위한 append-only 로그 — 이의제기 처리 시 근거 자료)*
- **DisputeTicket**: id, round_id, raised_by, reason, status(open/reviewing/closed) *(정답 수정이 아니라 별도 트랙으로 처리됨을 데이터 구조로도 강제)*

## 8. API 연동 상세 (소다기프트)

**카탈로그 구성 시 전체 상품 조회**
```
GET /v1/products
```

**예산 게이트 — 잔액 확인**
```
GET /v1/accounts/balance
```

**지급 현황 — 개별 주문 상태 확인 (지급 모니터링 화면 폴링용)**
```
GET /v1/orders/{id}
```

**지급 실패 재시도 — 유저앱과 동일한 멱등키로 재호출**
```
POST /v1/orders
Header: SODA-API-KEY
{
  "item": { "id": <선택된 product id> },
  "delivery": { "method": "EMAIL", "recipient": {...}, "sender": { "name": "SodaPick" } },
  "message": "...",
  "external_reference_id": "sodapick_{campaign_id}_{participant_id}"  // 유저앱과 동일 규칙 유지
}
```

> 참고: 스폰서 앱은 직접 `POST /v1/orders`를 호출하지 않고(그건 유저앱의 클레임 완료 시점에 실행됨), 실패 건에 한해 "재시도" 액션을 통해 동일 호출을 트리거하는 역할만 한다 — 지급 실행 주체는 항상 참가자의 클레임 확정 시점으로 통일해 판정 로직의 단일 진실 공급원을 유지한다.

## 9. 비기능 요구사항

- 데스크탑 우선 반응형 (스폰서 담당자는 대부분 업무용 PC로 접속할 것으로 가정 — 유저앱과 반대)
- 판정 확정 액션은 감사로그(`ResolutionAuditLog`)에 append-only로 기록, 삭제/수정 API 자체를 만들지 않음
- 예산 게이트는 클라이언트단 검증에 의존하지 않고 발행 API 호출 시점에 서버에서 최종 재검증
- 발행 후 수정 불가 필드는 프론트 UI 비활성화뿐 아니라 백엔드에서도 거부하도록 이중 방어

## 11. MVP 컷라인 (해커톤 3분 데모 기준)

**반드시 있어야 함**: 캠페인 생성 마법사(5.2, 라운드 설계+카탈로그 구성 포함) → 예산 게이트(5.5) → 라운드 판정 콘솔(5.7, 미리보기 포함) → 지급 현황(5.8)

**포함하기로 확정 (2단계 요소)**
1. 예산 게이트 경고/안심 배너 — 구현 비용 대비 "이 제품이 사고를 막아준다"는 신뢰 메시지 임팩트가 가장 큼
2. 판정 확정 더블 컨펌 모달 — 거의 공짜로 "판정 불변성"이라는 설계 원칙을 시각적으로 증명 가능
3. 캠페인 종료 리포트 — 하드코딩된 요약 수치만으로도 "완성된 제품" 느낌 가능

**시간 부족 시 가장 먼저 쳐낼 항목**: 지급 실패 재시도 UI(발표에서는 "실패 건은 재시도 로직이 있다"고 말로만 설명해도 충분), 팀원 권한 관리(5.10, 애초에 스코프 밖)

**여전히 없어도 데모 가능**: 이의제기(DisputeTicket) 처리 화면 자체 — 데이터 모델과 "판정은 되돌릴 수 없다"는 원칙만 발표에서 짚으면 됨, UI까지 만들 필요는 없음
